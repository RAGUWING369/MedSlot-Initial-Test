# ADR-004: Authentication Strategy — SMS OTP + Stateless JWT

**Status:** Accepted
**Date:** 2026-05-25
**Deciders:** Tech Lead, Product Owner, Security Lead

---

## Context

MedSlot must authenticate two types of users (patients and doctors) on a web application targeting urban Indian adults. The authentication mechanism must:
- Not require passwords (confirmed by the Product Owner — reduces friction for first-time users and eliminates password management overhead)
- Not use social login (Google/Facebook) — some patients and doctors prefer not to link their healthcare activity to social identities
- Work reliably on Indian mobile networks via SMS
- Issue tokens that encode the user's role for RBAC enforcement across all API endpoints
- Satisfy NFR-SEC-004 (SMS OTP only), NFR-SEC-005 (RBAC), NFR-SEC-006 (24h JWT TTL), NFR-SEC-007 (OTP rate limit)
- Support a 3-person team without a dedicated identity service

The constraint is explicit in CLAUDE.md: "Authentication: SMS OTP via MSG91 for both patients and doctors — no social login (Google/Facebook)."

---

## Decision

**Authentication mechanism:** SMS OTP via MSG91

**Token format:** JSON Web Token (JWT), HS256 signed, 24-hour expiry

**Token contents:**
```json
{
  "sub": "<user_uuid>",
  "role": "patient|doctor|admin",
  "iat": <issued_at_unix>,
  "exp": <expiry_unix>
}
```

**Storage:** JWT stored in the client as an HTTP-only cookie OR Authorization header — frontend uses `Authorization: Bearer <token>`. No refresh tokens in v1 (24h TTL is acceptable for this use case; re-authentication via OTP is quick).

**OTP lifecycle:**
1. Client posts phone number to `POST /api/v1/auth/otp/request/`
2. Backend generates 6-digit OTP, stores hashed OTP + expiry in Redis key `otp:{phone}` with 5-minute TTL
3. Backend increments rate-limit counter `otp_rate:{phone}` with 60-minute TTL; rejects if counter ≥ 5
4. MSG91 sends OTP via SMS
5. Client posts OTP to `POST /api/v1/auth/otp/verify/`
6. Backend verifies OTP hash against Redis, checks expiry, checks failure counter
7. On success: Django creates or retrieves the user record; issues JWT; deletes Redis OTP key
8. On failure: increments failure counter `otp_fail:{phone}`; after 3 failures in 10 minutes, locks further requests for 15 minutes

**Rate limiting implementation:** Redis TTL-based counter per phone number key (A-02-014). Two counters:
- `otp_rate:{phone}` — generation rate limit (5 per 60 min, BR-005)
- `otp_fail:{phone}` — verification failure counter (3 per 10 min → 15-min lockout, BR-002)

**Authorization enforcement:**
- Django REST Framework permission classes, applied at the view level (never just at the frontend)
- `IsPatient` — requires `token.role == 'patient'`
- `IsApprovedDoctor` — requires `token.role == 'doctor'` AND `DoctorProfile.account_status == 'Approved'`
- `IsAdmin` — requires `token.role == 'admin'`
- Public endpoints (doctor search, doctor profile, OTP initiation): no authentication required

**JWT signing key:** HS256 with a 256-bit random secret stored in AWS Secrets Manager at `/medslot/prod/django` (SECRET_KEY). Never hardcoded in source or Docker images.

## Rationale

**OTP over password:**
- Indian mobile penetration is near-universal; OTP login removes the password management burden entirely
- MedSlot targets users who may not use password managers — an OTP-only flow reduces abandoned registrations (aligns with OTP registration completion rate ≥ 75% success metric)
- The healthcare context makes password breaches particularly harmful; OTP eliminates the password attack surface entirely

**Stateless JWT over session cookies:**
- Next.js frontend and Django backend run as separate ECS services; stateless JWT avoids shared session store synchronization
- JWT is already carried in the Redis cache layer (OTP state); adding session state would increase Redis load and add a cross-service dependency
- 24-hour TTL is appropriate for a web application where users return within a day; no sensitive financial transactions require shorter TTL

**HS256 over RS256:**
- v1 has a single backend service verifying tokens — asymmetric keys (RS256) would benefit multi-service architectures where services need to verify tokens without access to the secret key
- Modular monolith: all verification happens in the Django app; HS256 is simpler and equally secure for this pattern
- Can be upgraded to RS256 if service extraction occurs post-v1

**No refresh tokens in v1:**
- Refresh tokens add implementation complexity (token rotation, revocation lists)
- Users who lose their session simply re-authenticate via OTP — this is fast (< 30 seconds) and acceptable for a non-financial application
- Re-evaluate if user feedback indicates re-authentication friction is a drop-off point

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| Username + Password | Familiar UX | Password management overhead; credential stuffing attack surface; GDPR-level password storage complexity; higher first-time registration abandonment | Explicitly out of scope (CLAUDE.md) |
| Google / Facebook OAuth | One-click login | Users link healthcare activity to social identity (privacy concern); requires OAuth infrastructure; not all patients have Google/Facebook accounts | Explicitly out of scope (CLAUDE.md) |
| Session-based auth (Django sessions) | Built-in Django support | Requires shared session store accessible by all ECS tasks; stateful; adds Redis key coordination overhead; incompatible with stateless horizontal scaling | Stateful; incompatible with multiple ECS tasks |
| Refresh token rotation | Longer-lived sessions without 24h re-auth | Implementation complexity; revocation list storage in Redis; overkill for v1 usage pattern | Add in v2 if 24h TTL causes user friction |
| Email OTP (instead of SMS) | Lower cost | Lower delivery speed (email can have variable delay); less familiar to Indian users accustomed to SMS OTP | User expectation is SMS; email OTP has higher drop-off in Indian market |

---

## Consequences

**Positive:**
- Zero password storage — eliminates the entire credential breach risk vector
- OTP rate limiting via Redis is the same infrastructure used for slot availability cache — no additional component
- RBAC at the view level means authorization logic is co-located with the endpoint definition — easy to audit and test
- No session state to synchronize across ECS tasks — horizontal scaling is trivial

**Negative:**
- Users whose SIM cards are lost/stolen cannot authenticate until they recover the number (acceptable — same as any OTP-based system)
- 24-hour TTL means sessions survive even after a user realizes their device has been compromised; mitigated by the attacker also needing the phone number to initiate a new OTP

**Future:**
- Add biometric authentication (WebAuthn/FIDO2) as a second factor for doctor accounts — prescription issuance is a higher-stakes action
- Evaluate refresh token rotation when session length feedback indicates 24h causes friction
