# ADR-001: Architectural Pattern — Modular Monolith

**Status:** Accepted
**Date:** 2026-05-25
**Deciders:** Tech Lead, Full-Stack Lead, Backend Engineer

---

## Context

MedSlot is a new greenfield platform with a 3-person development team and a hard deadline of 2026-10-31. The team must deliver a complete patient booking flow, doctor consultation workflow, prescription generation, health record management, subscription billing, and an admin verification panel — all before go-live.

The product serves a single Indian market, targets 200–800 active users at launch with a peak NFR of 500 concurrent users (NFR-PE-006), and all six business domains (auth, appointments, consultations, prescriptions, records, subscriptions) share transactional state — for example, issuing a prescription atomically marks the appointment Completed and triggers an async PDF job. These are co-located domain operations, not independently deployable services.

The forces at play:
- Team constraint: 3 developers cannot sustain independent CI/CD pipelines, separate service repositories, distributed tracing infrastructure, and network contracts across services
- All domains require database transactions that span multiple entities
- Time constraint: microservice overhead (service mesh, API contracts, distributed logging) would consume 30–40% of the team's capacity on infrastructure rather than product
- Scale constraint: 500 concurrent users is well within the capacity of a single optimized application instance, let alone a cluster
- Growth path: domain boundaries must be clean enough for future service extraction if the team scales to 10+ engineers post-Series A

---

## Decision

Adopt a **Modular Monolith** architectural pattern:

- Single deployable backend unit: Django 5 application with six distinct internal Django apps, each owning its models, serializers, views, services, and tests
- Single deployable frontend unit: Next.js 14 App Router application
- Two async workers: Celery Worker (PDF generation, email dispatch) and Celery Beat (scheduled jobs — slot regeneration, appointment reminders)
- All services run as separate ECS Fargate task definitions from the same Docker image (worker and beat from the backend image)

Django app boundaries:
- `accounts/` — CustomUser, PatientProfile, DoctorProfile, OTP auth, JWT issuance
- `appointments/` — AvailabilityCalendar, AppointmentSlot, Appointment, consultation start
- `prescriptions/` — ConsultationNote, Prescription, PDF Celery task
- `records/` — HealthRecord, S3 pre-signed upload/download
- `notifications/` — SendGrid email, MSG91 SMS, Celery tasks, audit-safe dispatch
- `subscriptions/` — DoctorSubscription, Razorpay webhook handler
- `analytics/` — AnalyticsEvent write endpoint and server-side event helpers
- `audit/` — AuditLog model and signal receivers

Cross-app imports are permitted only in the inward direction (outer apps may import from `accounts/`; `accounts/` does not import from `appointments/`). Circular imports between apps are forbidden.

---

## Rationale

| Criterion | Evidence |
|-----------|----------|
| Team size | 3 developers cannot sustain microservice ops overhead (CLAUDE.md: "3 developers — 1 full-stack lead, 1 frontend, 1 backend") |
| Scale target | 500 concurrent users (NFR-PE-006) is addressable by 2–4 ECS Fargate tasks with auto-scaling — no partitioned compute required |
| Transactional integrity | Prescription issuance must atomically update ConsultationNote, Prescription, and Appointment in a single database transaction — impossible across service boundaries without distributed transaction protocols |
| Timeline | 2026-10-31 deadline (CLAUDE.md) — modular monolith ships in 1 sprint cycle what microservices would require 2–3 for infrastructure setup alone |
| Future extraction | Clean app boundaries mean: when team grows to 10+, `prescriptions/` can be extracted to a separate service without rewriting interfaces — the interface is the DRF serializer + service layer, not a tightly coupled SQL join |

---

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| Microservices | Independent scaling per service; team autonomy | Requires distributed tracing, service mesh, separate CI/CD per service, network contract testing; adds 40%+ ops overhead for a 3-person team | Over-engineered for team size and scale; rejected per ADR-001 rationale |
| Pure Monolith (no app boundaries) | Simplest to start | Accumulates coupling debt rapidly; extraction becomes a rewrite at scale | Rejected — clean app boundaries are necessary to avoid a big ball of mud at 12 months |
| Serverless (Lambda + API Gateway) | Near-zero infra management; pay-per-request | Cold starts incompatible with NFR-PE-001 (P95 ≤ 200ms); WeasyPrint cannot run in Lambda (binary size + execution time); higher per-invocation cost at sustained 500 CCU | Technical and cost incompatibility |
| Event-Driven (CQRS + event sourcing) | Full audit trail; decoupled reads and writes | Steep learning curve; operational complexity far exceeds requirements for v1; team of 3 cannot build and maintain an event store | Over-engineered for requirements and team |

## Consequences

**Positive:**
- All six domains share a single PostgreSQL transaction — prescription issuance, appointment status update, and PDF queuing can be wrapped in `atomic()` with no two-phase commit
- Single deployment pipeline; one ECS service definition for the API; one for the worker
- Django's ORM, admin, and signal system work natively across all app models
- Test suite is simpler: no service mocking needed for cross-domain integration tests

**Negative:**
- No independent scaling per domain — if PDF generation demand spikes, the whole worker scales, not just the PDF component (acceptable at v1 scale)
- Future service extraction requires a database-level split, not just a code split — this must be managed as a deliberate migration project if the team grows

**Future:**
- When prescriptions domain reaches >1,000 PDF/day or the team grows: extract `prescriptions/` worker as a separate service with its own ECS task definition and its own PostgreSQL schema; the existing DRF API contract remains unchanged
- The `subscriptions/` webhook handler is the most likely first extraction candidate given Razorpay's independent SLA requirement
