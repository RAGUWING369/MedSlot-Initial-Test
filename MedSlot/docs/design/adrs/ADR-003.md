# ADR-003: Database Engine — PostgreSQL 16 on AWS RDS

**Status:** Accepted
**Date:** 2026-05-25
**Deciders:** Tech Lead, Backend Engineer

---

## Context

MedSlot requires a relational database engine that supports:
- UUID primary keys across all tables (security requirement: no sequential ID enumeration)
- JSONB columns for medicines array (Prescription), working hours (AvailabilityCalendar), and analytics event properties (AnalyticsEvent)
- Row-level locking for concurrent appointment slot booking (FR-BOOK-002)
- Full ACID transactions for prescription issuance (atomic update across ConsultationNote, Prescription, Appointment)
- AWS managed service for operational simplicity with a 3-person team
- RPO ≤ 30 minutes (NFR-REL-003) via automated backups + PITR
- Encryption at rest AES-256 (NFR-SEC-002)

---

## Decision

Use **PostgreSQL 16** on **AWS RDS**, deployed as a Multi-AZ instance in ap-south-1.

**Configuration:**
- Instance class: `db.t3.medium` (2 vCPU, 4GB RAM)
- Storage: 50GB gp3, auto-scaling enabled (ceiling: 200GB)
- Multi-AZ: enabled — synchronous standby in ap-south-1b for automatic failover
- Backups: automated daily snapshots; PITR enabled (30-minute granularity satisfies NFR-REL-003)
- Encryption: AWS RDS encryption enabled at provisioning (AES-256, AWS KMS — satisfies NFR-SEC-002)
- Parameter group: `max_connections=200`, `shared_buffers=1GB`, `work_mem=16MB`
- Connection handling: Django's built-in database connection pooling (CONN_MAX_AGE=60s); PgBouncer added if connections saturate at scale

**Migrations:** Django's built-in migration system. Every schema change requires a migration file. Destructive migrations (DROP COLUMN, DROP TABLE) require an explicit human review gate. No migration runs automatically on deployment without a dry-run step.

---

## Rationale

| Requirement | PostgreSQL 16 Capability |
|-------------|-------------------------|
| UUID PKs | Native `gen_random_uuid()` function; UUID type in all tables |
| JSONB | Native JSONB with GIN indexes — used for medicines[], working_hours, analytics properties |
| Row-level locking | `SELECT ... FOR UPDATE NOWAIT` — used in concurrent booking (FR-BOOK-002) |
| ACID transactions | Full MVCC transaction isolation; Django's `atomic()` maps directly |
| Soft delete queries | Partial indexes (`WHERE is_deleted = false`) for efficient health record queries |
| Full-text search | PostgreSQL FTS for future doctor search enhancement (not required v1, but available) |
| AWS managed | RDS provides automated failover, patching, backup, encryption |

---

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| MySQL 8 (AWS RDS) | Widely used; good AWS support | JSONB support weaker (JSON type, no GIN index); row-level lock semantics differ from PostgreSQL; Django ORM has known MySQL quirks with UUID handling | Functional but inferior for MedSlot's JSONB usage pattern |
| AWS Aurora PostgreSQL (Serverless v2) | Auto-pause saves cost at low traffic; auto-scaling | Minimum ACU cost higher than db.t3.medium at sustained usage; cold start latency from paused state is incompatible with NFR-PE-001 (P95 ≤ 200ms) | Aurora Serverless cold-start incompatible with latency NFR |
| AWS Aurora PostgreSQL (Provisioned) | Higher throughput; fast failover | 2–3× cost of RDS PostgreSQL at equivalent instance size; overkill at 500 CCU; exceeds budget if multiple services needed | Cost-disproportionate for v1 scale |
| MongoDB (AWS DocumentDB) | Flexible schema | ACID transactions less mature; Django ORM requires Djongo (unmaintained); no row-level locking equivalent; relational integrity for appointment state machine requires transactions | No Django ORM support; transaction model weaker |
| SQLite | Zero infra overhead | Single-process only; no concurrent write support; not viable for production | Development only; production-incompatible |

---

## Consequences

**Positive:**
- Single source of truth for all relational data, transactional state, and analytics events
- JSONB eliminates the need for a separate document store for medicines and analytics
- AWS RDS Multi-AZ provides automatic failover (typically < 2 minutes), satisfying NFR-REL-002 (RTO ≤ 1 hour)
- PITR satisfies NFR-REL-003 (RPO ≤ 30 minutes) out of the box

**Negative:**
- db.t3.medium is burstable CPU — sustained CPU-intensive workloads (unlikely at launch scale) can exhaust burst credits; monitor CPU credit balance in Phase 13
- No read replica at launch: all reads and writes hit the primary; add read replica when read:write ratio exceeds 5:1 (estimated at ~5,000+ active users)

**Future:**
- Add PgBouncer transaction-mode connection pooling when active connections approach 150 (80% of max_connections=200)
- Evaluate read replica when query load exceeds 70% average CPU on primary
