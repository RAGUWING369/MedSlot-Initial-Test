# ADR-008: Analytics Storage — PostgreSQL analytics_events Table (No Third-Party SDK)

**Status:** Accepted
**Date:** 2026-05-25
**Deciders:** Tech Lead, Product Owner

---

## Context

MedSlot requires product analytics to measure KPIs defined in SUCCESS-METRICS.md and the PRD-ANALYTICS-PLAN.md: booking funnel conversion (≥ 60%), OTP registration completion (≥ 75%), consultation completion rate (≥ 70%), prescription download rate (≥ 80%).

Two architectural options exist:
1. Integrate a third-party analytics SDK (Mixpanel, Amplitude, Segment, GA4, PostHog)
2. Store analytics events in a dedicated PostgreSQL table within the existing database

PHI compliance constraint (BR-019, NFR-SEC-011): No PHI may appear in analytics event properties. Third-party SDKs transmit event data to external servers — any accidental PHI inclusion becomes a data breach risk that MedSlot cannot remediate after the fact.

The analytics data requirements are defined in PRD-ANALYTICS-PLAN.md: 11 event areas, 4 funnel definitions, 3 dashboards. All analytics queries are SQL-based and run against the same PostgreSQL instance used for operational data.

---

## Decision

Store all analytics events in a dedicated **`analytics_events` table in the primary PostgreSQL database** (a dedicated schema: `analytics`). No third-party analytics SDK is integrated in v1.

**Rationale for schema isolation:**
- `analytics_events` table lives in the `analytics` PostgreSQL schema, separate from the `public` schema used for operational tables
- This prevents accidental JOINs between operational (PHI-bearing) tables and analytics events
- Retention policy (24 months — A-03-003) can be enforced via a single DELETE query scoped to the `analytics` schema

**Event write paths:**
- Server-side state-change events: written synchronously within Django service methods (same DB transaction as the state change)
- Post-processing events (PDF generation completion, email sent): written by the Celery worker task
- Client-side UX events: written via `POST /api/v1/analytics/events/` — JWT required for authenticated events; rate-limited unauthenticated endpoint for pre-login funnel steps

**Dashboard access:** Direct SQL queries against the `analytics.analytics_events` table via a read-only PostgreSQL user. No BI tool in v1 (A-03-011). Dashboard queries are authored by the Tech Lead and run manually or as scheduled reports. Materialized views added if query performance degrades.

**Data governance:**
- PII rules from PRD-ANALYTICS-PLAN.md Section 6 are enforced in code: `user_id` (UUID) only, no names/phones in properties, no PHI field values
- A custom Django serializer validates analytics event properties against an allowlist before write
- The `analytics.analytics_events` table has no foreign key constraints to PHI-bearing tables (only soft UUID references to `users.id`) — this prevents analytics retention from being tied to user data retention periods

---

## Rationale

**Against third-party SDK:**

| Risk | Impact | Mitigation if SDK used |
|------|--------|----------------------|
| Accidental PHI in event properties | Data breach; regulatory liability | Requires continuous audit of every event sent; error-prone |
| Third-party data processing | Data processed outside India; potential DISHA concern | Would require BAA/DPA with each vendor |
| Additional cost | Mixpanel/Amplitude free tiers are limited; paid tiers add $100–500/month | Exceeds need for v1 analytics |
| SDK bundle size | Adds 30–80KB to frontend bundle; affects NFR-PE-002/PE-003 | Tree-shaking helps but not eliminates |
| Vendor lock-in | Event schema and funnel definitions tied to vendor format | Migrating analytics history is expensive |

**For PostgreSQL table:**

| Benefit | Evidence |
|---------|----------|
| PHI risk eliminated | Events never leave MedSlot's infrastructure |
| Zero additional cost | Uses existing RDS PostgreSQL instance |
| SQL for analysis | Same language as operational queries; no new tool for the team to learn |
| Schema flexibility | JSONB `properties` column accommodates all event types without schema migration |
| Sufficient for v1 scale | 60 events/day at launch × 365 days × 24 months = ~438,000 rows — trivially small for PostgreSQL |

---

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| Mixpanel / Amplitude | Rich visualization; funnels built-in; no SQL needed | PHI exposure risk; third-party data transfer; $100–500/month at scale; vendor lock-in | PHI risk and cost not justified for v1 |
| PostHog (self-hosted) | Open source; no data transfer; good funnel analysis | Additional infrastructure to maintain (ClickHouse or PostgreSQL + PostHog app); too much ops overhead for a 3-person team at launch | Ops overhead disproportionate |
| Google Analytics 4 | Free; powerful event model | Third-party data transfer; PHI-adjacent events require careful filtering; not appropriate for a healthcare-adjacent application | PHI risk; Google data processing terms |
| Separate ClickHouse instance | Columnar DB optimized for analytics | Additional infrastructure; learning curve; overkill for v1 event volumes (< 1M events/year) | Over-engineered for v1 scale |

---

## Consequences

**Positive:**
- PHI risk is contained within MedSlot's infrastructure boundary
- Analytics schema is fully under MedSlot's control — event definitions can be added/changed without SDK upgrades
- No additional cost beyond existing RDS instance

**Negative:**
- No built-in visualization — dashboards require manual SQL query authorship (acceptable for v1 with a technical ops team)
- JSONB query performance degrades if the analytics table grows beyond ~10M rows without a dedicated read replica or materialized views; monitor and add materialized views at ~5M rows

**Future:**
- If analytics volume exceeds 10M rows or visualization needs grow: migrate to PostHog self-hosted (ClickHouse backend) and import historical events via export script
- If the team wants a visual funnel tool without the PHI risk: evaluate Plausible (privacy-first, no personal data) for UX funnel only, keeping PHI-adjacent events in PostgreSQL
