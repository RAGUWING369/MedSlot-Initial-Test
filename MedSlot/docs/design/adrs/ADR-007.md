# ADR-007: Admin Panel — Extended Django Admin (Not Custom React Frontend)

**Status:** Accepted
**Date:** 2026-05-25
**Deciders:** Tech Lead, Product Owner

---

## Context

MedSlot requires an Admin Panel for MedSlot Operations staff to:
- View and verify pending doctor applications (FR-ADMIN-001)
- Approve or reject doctor registrations (FR-ADMIN-002, FR-ADMIN-003)
- Suspend and reactivate doctor accounts (FR-ADMIN-004, FR-ADMIN-005)
- Access credential documents (S3 link)

The admin interface is used exclusively by the MedSlot internal team (Admin User persona). It is not a customer-facing product. The user count is ≤ 5 internal staff. The visual quality bar is functional, not polished.

Building a custom React admin panel would require:
- Separate Next.js routes and pages (minimum 3–4 screens)
- API endpoints specifically for admin reads/writes (already required, but UI scaffolding is additional)
- Form components, table components, navigation — all custom UI work
- Estimated effort: 2–3 engineering weeks for the full admin UI

The FEASIBILITY-REPORT.md Phase 1 risk mitigation explicitly identified: "Build admin panel as a thin Django admin view" to reduce frontend time budget. This was recorded as assumption A-02-011 (confirmed Medium confidence). The Phase 4 pre-design confirmation did not override this.

---

## Decision

Implement the Admin Panel using **Django's built-in admin framework**, extended with custom ModelAdmin classes for the doctor verification workflow.

**Implementation specifics:**
- `DoctorProfile` registered with a custom `DoctorVerificationAdmin` class
- Custom actions: "Approve Selected Doctors", "Reject Selected Doctors" (with inline reason field), "Suspend Account", "Reactivate Account"
- Custom list display: doctor name, specialty, city, MCI number, account status, submission date, credential document link
- Custom detail view: inline credential document download (S3 pre-signed URL generated on view)
- Read-only fields: MCI number, phone, submission date (admin cannot edit these via UI)
- Audit logging: every status change triggers an AuditLog record (NFR-MAIN-004)
- Admin panel protected at `/admin/` path, served by the Django API ECS service
- Access requires `is_staff=True` + `is_superuser=False` (or a dedicated admin group) — never accessible via Patient or Doctor JWT

**Django admin URL:** `https://medslot.in/admin/` (ALB path-based routing forwards `/admin/*` to the Django API service)

---

## Rationale

| Factor | Django Admin | Custom React Admin |
|--------|-------------|-------------------|
| Build time | 2–3 days of custom ModelAdmin code | 2–3 weeks of UI + API work |
| UX | Functional — adequate for internal ops team | Polished — over-engineered for 5 internal users |
| Maintenance | Django admin evolves with Django; zero frontend maintenance | Custom React admin requires separate frontend maintenance alongside the patient/doctor UI |
| Test coverage | Django admin views are covered by Django's own test suite; custom actions require only unit tests for the action logic | Full E2E tests needed for the custom UI |
| Security | Django admin has decades of hardening; CSRF protection, session management, and access control are built in | Must be re-implemented in the custom frontend |

The 2–3 week savings from using Django Admin directly contributes to meeting the 2026-10-31 deadline (CLAUDE.md). For a 3-person team, this is a significant allocation.

---

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| Custom React admin panel (in Next.js) | Consistent design language with patient/doctor UI; more flexible workflows | 2–3 weeks build time; adds complexity to the frontend codebase; over-engineered for ≤5 internal users | Timeline cost not justified by the user count or UX requirement |
| Third-party admin panel (AdminJS, React Admin) | Pre-built UI components; faster than fully custom | Additional dependency; customization for approval workflow requires significant configuration; security audit overhead for an additional library in a healthcare context | Dependency overhead without sufficient benefit |
| Retool / Appsmith (no-code admin) | Zero engineering time | Third-party data access to PHI-adjacent data (doctor credentials, MCI numbers); data sovereignty concern; recurring tool cost | Data sovereignty and PHI-proximity risk in a healthcare context |

---

## Consequences

**Positive:**
- Admin panel delivered in days, not weeks — frees frontend engineer for patient/doctor UI
- Django admin's built-in change history provides a free audit trail of all admin actions (supplements AuditLog model)
- Zero additional frontend dependencies or routes

**Negative:**
- Admin panel has the default Django admin visual style — not consistent with the MedSlot brand
- Complex workflows (e.g., displaying a credential PDF inline) require custom template overrides, which take more effort than they appear
- Django admin is not optimized for mobile — acceptable since admin tasks are performed on desktop only

**Future:**
- If admin team grows to > 20 users or requires complex workflows (multi-step approval, analytics dashboards): build a custom admin panel in Phase 2
- Django admin remains in place as a superuser escape hatch even if a custom admin is built later
