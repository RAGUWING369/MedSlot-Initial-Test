# ADR-002: Technology Stack

**Status:** Accepted
**Date:** 2026-05-25
**Deciders:** Tech Lead, Full-Stack Lead, Backend Engineer

---

## Context

The technology stack was specified in CLAUDE.md prior to Phase 4. This ADR formalizes the stack choices with comparative justification and documents the alternatives considered for each layer. All choices were confirmed as current in the Phase 4 pre-design confirmation.

The stack must satisfy:
- Web-first, desktop-first application (NFR-USE-004)
- SEO requirement on doctor discovery pages (PRD — doctor search must be discoverable)
- 90% test coverage minimum (NFR-MAIN-001)
- OpenAPI 3.0 spec auto-generation (NFR-MAIN-002)
- Structured JSON logging (NFR-MAIN-003)
- Server-side prescription PDF generation (FR-RX-003)
- SMS OTP via Indian provider (FR-AUTH-001; MSG91 chosen for India-specific reliability)

---

## Decision

Accept the stack specified in CLAUDE.md as the canonical technology stack for MedSlot v1.

### Frontend
- Language: TypeScript 5 (strict mode)
- Framework: Next.js 14 (App Router)
- UI: Tailwind CSS 3
- State: Zustand 4

### Backend
- Language: Python 3.12
- Framework: Django 5.x + Django REST Framework 3.15
- Task queue: Celery 5.x with Redis 7 as broker
- PDF: WeasyPrint 60.x
- OpenAPI: drf-spectacular
- Logging: python-json-logger

### Data
- Primary DB: PostgreSQL 16 (AWS RDS)
- Cache / broker: Redis 7 (AWS ElastiCache)

### Infrastructure
- Compute: AWS ECS Fargate (ap-south-1)
- Storage: AWS S3
- CDN: AWS CloudFront
- Secrets: AWS Secrets Manager

### Integrations
- Email: SendGrid v3
- SMS/OTP: MSG91 v5
- Billing: Razorpay Subscriptions

## Rationale

### TypeScript + Next.js 14

Next.js 14 App Router provides server-side rendering for doctor discovery pages (SEO-critical — patients discovering doctors through search engines) and client-side rendering for authenticated dashboards (interactive, no SEO requirement). No other React framework provides this SSR/CSR hybrid with the same ecosystem maturity. TypeScript strict mode prevents entire classes of runtime errors common in healthcare data handling.

### Django + DRF

Django provides an integrated ORM, admin framework, signals, and migration system — all used by MedSlot. The Django admin is used as the admin panel (ADR-007), saving 2–3 weeks of frontend development. DRF provides RBAC permission classes that map directly to MedSlot's three-role model. Python 3.12 is the latest stable version with significant performance improvements (10–60% over 3.10) that contribute to meeting NFR-PE-001.

### Celery + Redis

Celery is the industry-standard task queue for Django applications. Required for: async PDF generation (A-02-009, A-03-005), email dispatch with retry (NFR-REL-004), daily slot regeneration (FR-CAL-005), and appointment reminders (FR-NOTIF-006). Redis serves dual purpose as Celery broker and application cache (slot availability TTL, OTP rate limiting). Eliminates a separate message queue service.

### PostgreSQL 16

PostgreSQL 16 provides: UUID support (no sequential ID exposure risk), JSONB for medicines array and analytics event properties, row-level locking for concurrent booking (FR-BOOK-002), full ACID transactions for prescription issuance, and mature AWS RDS management. Version 16 provides improved query parallelism and I/O performance vs. 15.

### WeasyPrint 60.x

WeasyPrint renders HTML templates to PDF server-side using CSS Paged Media. Enables the prescription PDF template to use the same Tailwind-like CSS as the frontend, ensuring visual consistency. Runs in the Celery worker process (not in the HTTP request lifecycle) to meet NFR-PE-004 (≤ 4s P95). See ADR-006 for the async PDF decision.

## Alternatives Considered

| Layer | Alternative | Why Rejected |
|-------|-------------|-------------|
| Frontend framework | React + Vite (SPA) | No SSR for doctor discovery pages — SEO requirement is unmet; patient search traffic from Google requires crawlable HTML |
| Frontend framework | Remix | Smaller ecosystem; Zustand integration less mature; team has Next.js experience |
| Backend framework | FastAPI (Python) | No built-in admin panel; ORM (SQLAlchemy) requires additional setup; DRF's permission system maps more directly to MedSlot's RBAC model; Django admin saves 2–3 weeks of admin panel work |
| Backend framework | Node.js (NestJS) | TypeScript everywhere is appealing, but Python's data science / ML ecosystem is a future option for prescription analytics; WeasyPrint is Python-native; Django Admin not available |
| PDF generation | Puppeteer (headless Chrome) | Requires Chromium binary in ECS task (~130MB); higher memory requirement; not Python-native; WeasyPrint is lighter and Python-native |
| PDF generation | ReportLab | Code-based PDF construction (not HTML/CSS); harder to maintain prescription template; design flexibility requires significant boilerplate |
| Task queue | Django Q | Less mature than Celery; smaller community; fewer deployment options on ECS |
| Task queue | Amazon SQS + Lambda | Lambda cold start incompatible with WeasyPrint memory requirements; tighter AWS coupling |
| Cache | Memcached | No sorted sets or TTL-per-key (needed for OTP rate limiting); no Pub/Sub; cannot serve as Celery broker |
| Database | MySQL 8 | JSONB support is weaker than PostgreSQL; row-level locking semantics differ; Django ORM generates more efficient queries for PostgreSQL; AWS Aurora PostgreSQL is the natural upgrade path |
| Billing | Stripe Subscriptions | Not available for Indian merchants without additional KYC; Razorpay is the market standard for India (INR billing, Indian payment methods) |
| SMS | Twilio | US-centric pricing; MSG91 is the Indian market leader with better SMS deliverability on Indian carrier networks |
| Secrets | AWS Parameter Store | Secrets Manager provides automatic rotation support (relevant for RDS credentials) and a cleaner permission model; cost difference is negligible at MedSlot's scale |

## Consequences

**Positive:**
- Entire backend in one language (Python) simplifies hiring and onboarding for the 3-person team
- Django Admin eliminates need for custom admin UI (ADR-007) — saves 2–3 weeks
- Redis dual-purpose (cache + Celery broker) reduces infrastructure components
- Next.js SSR satisfies SEO for doctor discovery without a separate static site generator

**Negative:**
- WeasyPrint requires careful memory management in the Celery worker task (see capacity planning — worker needs 2GB RAM vs. 1GB for the API task)
- Python runtime performance ceiling is lower than Go or Java at extreme scale; acceptable at 500 CCU but noted for future re-evaluation at 10,000+ CCU

**Future:**
- If prescription PDF volume exceeds 10,000/day: evaluate wkhtmltopdf or dedicated PDF microservice
- If API P95 degrades under scale: evaluate adding a read replica and connection pooler (PgBouncer)
