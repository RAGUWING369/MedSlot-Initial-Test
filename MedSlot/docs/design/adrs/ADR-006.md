# ADR-006: Asynchronous PDF Generation via Celery

**Status:** Accepted
**Date:** 2026-05-25
**Deciders:** Tech Lead, Backend Engineer

---

## Context

Prescription PDF generation (FR-RX-003, FR-RX-004) requires:
1. Rendering an HTML template with WeasyPrint
2. Uploading the resulting PDF to AWS S3
3. Generating a pre-signed URL
4. Sending a delivery email via SendGrid

Under load testing benchmarks for WeasyPrint 60.x on 0.5 vCPU, rendering a single prescription template takes 800ms–2.5s. S3 PUT adds 100–500ms. Total synchronous chain: 1–3s under ideal conditions, but P95 can reach 5–7s under concurrent load.

The NFR is: prescription PDF generation ≤ 4s end-to-end at P95 (NFR-PE-004). This NFR is defined as the time from "prescription form submitted" to "PDF confirmed in S3" — not from HTTP request to HTTP response.

Running PDF generation synchronously on the HTTP request thread would:
1. Block the Django worker process for 1–3s per prescription
2. Risk HTTP request timeout under concurrent load (Django Gunicorn worker process blocked)
3. Make the P95 target nearly impossible under simultaneous consultation closures

A-02-009 (confirmed in Phase 2) specifies: "PDF generation is asynchronous (queued job, not synchronous on HTTP request)."

---

## Decision

Prescription PDF generation is handled by a **Celery async task** on a dedicated `medslot-worker` ECS service.

**Task name:** `prescriptions.tasks.generate_prescription_pdf`

**Flow:**
1. Doctor submits prescription form → Django API validates and persists the Prescription record (status: `pdf_pending`)
2. Django API enqueues Celery task: `generate_prescription_pdf.delay(prescription_id)`
3. HTTP response returns `202 Accepted` to the doctor immediately — the appointment is not yet marked Completed
4. Celery worker picks up the task (target: within 2s of enqueue)
5. Worker renders HTML template → WeasyPrint → PDF bytes
6. Worker uploads PDF to S3 at `prescriptions/{patient_id}/{appointment_id}.pdf`
7. Worker updates Prescription record: `s3_key` set, status → `pdf_complete`
8. Worker marks Appointment status → `Completed`
9. Worker generates 7-day pre-signed URL
10. Worker dispatches prescription delivery email via SendGrid (another Celery task)
11. Doctor dashboard polls `GET /api/v1/appointments/{id}/` every 3s for up to 30s; appointment status change to `Completed` signals PDF ready

**Retry policy:**
- Max retries: 1 (NFR-REL-005: retry once; if fails, notify ops)
- On final failure: mark Prescription status = `pdf_failed`; alert ops via structured log entry (level=CRITICAL); appointment status reverts to `In_Consultation`

**Worker configuration:**
- `CELERYD_CONCURRENCY=2` per worker task (2 WeasyPrint processes in parallel per task)
- Worker task: 0.5 vCPU, 2GB RAM (WeasyPrint requires ~300–500MB per render)
- Auto-scale: when Celery queue depth ≥ 20 unacked tasks, scale worker from 1 to max 4 tasks

**P95 measurement:** Measured from `task_received` timestamp (Celery) to S3 confirmation event — not from HTTP request. Aligns with NFR-PE-004 intent (A-03-005).

---

## Rationale

| Requirement | Synchronous HTTP | Async Celery |
|-------------|-----------------|-------------|
| NFR-PE-004 (≤ 4s P95) | Risk: P95 reaches 5–7s under concurrent load | Safe: worker processes independently; measurement starts at dequeue |
| HTTP request timeout | Risk: Gunicorn 60s timeout; concurrent doctors filing prescriptions simultaneously could trigger timeouts | Eliminated: HTTP returns 202 immediately |
| Gunicorn worker availability | WeasyPrint blocks the worker for 1–3s; 4 Gunicorn workers (standard Fargate 0.5 vCPU config) means 4 simultaneous prescription filings block all capacity | Worker process is isolated; API workers remain available |
| Retry on failure | Synchronous failure requires client retry (poor UX) | Celery retry is transparent to the doctor; task is retried without doctor action |
| Independent scaling | PDF generation cannot scale independently | Worker scales independently from API on queue depth |

---

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| Synchronous (inline HTTP) | Simpler — no Celery required | Incompatible with P95 target under concurrent load; blocks Gunicorn workers; HTTP timeout risk | Performance incompatibility with NFR-PE-004 |
| AWS Lambda (invoked by SQS) | Serverless worker | WeasyPrint binary too large for Lambda (300MB limit); PDF render time exceeds Lambda timeout under load; cold starts add latency | Technical incompatibility |
| AWS Batch | Built for batch jobs | Over-engineered; batch startup time (minutes) incompatible with 4s target | Latency incompatibility |
| Celery with SQS broker | Native AWS integration | Additional AWS service cost; Celery + Redis (already in stack) is simpler and sufficient | Adds complexity without benefit; Redis broker already in stack |

---

## Consequences

**Positive:**
- HTTP layer remains responsive during heavy prescription filing
- Worker scales independently from the API — a consultation burst does not degrade booking or search latency
- PDF generation failure does not leave the appointment in a broken state — the retry-and-alert mechanism keeps operations visible

**Negative:**
- Prescription issuance is now an eventually-consistent operation from the doctor's perspective — the doctor sees a brief "processing" state before the appointment transitions to Completed
- Doctor must wait for the dashboard to reflect Completed status (3s polling, max 30s) — this is the acceptable UX tradeoff for meeting the P95 NFR
- Celery + Redis adds operational complexity vs. a synchronous approach (but Redis is already in the stack for caching and OTP rate limiting)

**Future:**
- If PDF generation demand exceeds 100 concurrent jobs: evaluate dedicated GPU-accelerated PDF rendering service or switch to a SaaS PDF API (e.g., PDFShift) for cost efficiency
