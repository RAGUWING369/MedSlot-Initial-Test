# ADR-005: Deployment Platform — AWS ECS Fargate (ap-south-1)

**Status:** Accepted
**Date:** 2026-05-25
**Deciders:** Tech Lead, Full-Stack Lead

---

## Context

MedSlot must deploy containerized backend (Django) and frontend (Next.js) services with:
- High availability ≥ 99.9% uptime (NFR-REL-001)
- RTO ≤ 1 hour (NFR-REL-002)
- Auto-scaling to handle 500 CCU (NFR-PE-006)
- Indian data residency (ap-south-1 Mumbai — low latency for Indian users)
- $2,000/month AWS budget ceiling (CLAUDE.md constraint)
- A 3-person team that cannot sustain Kubernetes cluster administration

The application is composed of four logical deployment units: API (Django), Frontend (Next.js), Worker (Celery), and Beat (Celery Beat). All are containerized OCI images (NFR-PORT-001).

---

## Decision

Deploy all four services on **AWS ECS Fargate** in region **ap-south-1 (Mumbai)**.

**Service configuration:**

| Service | Image | Min Tasks | Max Tasks | vCPU | RAM | Auto-scale Trigger |
|---------|-------|-----------|-----------|------|-----|-------------------|
| medslot-api | backend:latest | 2 | 8 | 0.5 | 1GB | CPU ≥ 60% for 2 min |
| medslot-frontend | frontend:latest | 2 | 4 | 0.5 | 1GB | CPU ≥ 60% for 2 min |
| medslot-worker | backend:latest | 1 | 4 | 0.5 | 2GB | SQS/Celery queue depth ≥ 20 pending tasks |
| medslot-beat | backend:latest | 1 | 1 | 0.25 | 0.5GB | None (singleton) |

**Note:** medslot-worker uses 2GB RAM because WeasyPrint PDF generation requires more memory than the API tasks. All tasks use the same backend Docker image with different CMD entrypoints.

**Load balancing:** Application Load Balancer (ALB) in public subnet. Path-based routing:
- `/*` → medslot-frontend target group (port 3000)
- `/api/*` → medslot-api target group (port 8000)
- `/admin/*` → medslot-api target group (port 8000)
- `/api/schema/` → medslot-api target group

**Health checks:**
- API: GET /api/v1/health/ → 200 OK within 5s
- Frontend: GET / → 200 OK within 5s
- Worker: Celery worker inspect ping (ECS health check command)
- Beat: No external health check; ECS restarts on container exit

**ECR:** All images stored in AWS ECR (ap-south-1). Image tags: `{git_short_sha}`. Deployment via GitHub Actions: build → push to ECR → update ECS service (force new deployment).

---

## Rationale

**ECS Fargate over Kubernetes (EKS):**
A 3-person team cannot sustain Kubernetes cluster administration: node pool management, control plane upgrades, persistent volume management, and the operational learning curve. ECS Fargate provides managed container orchestration with no server management — tasks run on AWS-managed compute, auto-scale via Application Auto Scaling, and integrate natively with ALB, CloudWatch, and ECR. For a modular monolith (ADR-001) with four services, ECS Fargate is the right size.

**ECS Fargate over EC2-based ECS:**
Fargate eliminates EC2 instance management (patching, AMI updates, capacity reservation). The cost premium is justified by the operational time savings for a 3-person team. At 500 CCU scale, the Fargate per-vCPU cost is lower than EC2 Reserved + operational overhead.

**ap-south-1 (Mumbai):**
Target market is India. Mumbai is the closest AWS region to Bengaluru, Hyderabad, and Pune (confirmed launch candidates, OQ-001). Network latency from these cities to ap-south-1: 15–40ms vs. 80–150ms to ap-southeast-1 (Singapore). Directly impacts NFR-PE-001 (P95 ≤ 200ms).

**Multi-AZ task placement:**
ECS service placement strategy: `spread` across AZs. Minimum 2 tasks per service ensures that an AZ failure does not cause a service outage — satisfying NFR-REL-001 (99.9% uptime).

## Alternatives Considered

| Option | Pros | Cons | Why Rejected |
|--------|------|------|-------------|
| AWS EKS (Kubernetes) | Rich ecosystem; fine-grained control | Requires dedicated DevOps expertise; cluster admin overhead is disproportionate for a 3-person team; minimum viable EKS costs ~$150/month just for the control plane | Operational overhead incompatible with team size |
| AWS Lambda + API Gateway | Zero server management; auto-scaling to zero | Cold start latency incompatible with NFR-PE-001 (P95 ≤ 200ms); WeasyPrint binary/memory incompatible with Lambda; 15-minute execution limit incompatible with long PDF jobs | Technical incompatibility |
| AWS Elastic Beanstalk | Simpler than ECS; built-in load balancing | Less fine-grained control; harder to configure multi-service routing; auto-scaling is less predictable; ECS is the recommended successor for containerized apps | Less control; ECS is more aligned with IaC (Terraform) |
| Railway / Render / Fly.io | Developer-friendly; minimal config | No ap-south-1 region; data residency concern for Indian healthcare data; less control over VPC isolation and security group configuration | India region not available; data residency risk |
| AWS App Runner | Simpler than ECS; automatic VPC handling | Less control over subnet placement; cannot configure isolated subnets for RDS | Insufficient network isolation control for healthcare data |

## Consequences

**Positive:**
- No server patching or AMI management — AWS manages the compute layer
- Native ALB integration handles TLS termination, sticky sessions (not needed for JWT auth), and path-based routing
- ECS task roles provide IAM identity to containers — no static AWS credentials in environment (NFR-SEC-011)
- CloudWatch Container Insights provides task-level CPU/memory metrics for auto-scaling decisions (Phase 13)

**Negative:**
- Fargate task startup time is ~30–60s (container pull + runtime start) — slower than pre-warmed EC2 instances; mitigated by maintaining minimum 2 tasks per service
- Fargate cold-start on scale-out adds brief latency; mitigated by auto-scale triggering at 60% CPU (not 80%) to maintain buffer

**Future:**
- When team grows and MedSlot needs independent service deployments: migrate individual services to separate ECS services with independent deployment pipelines — infrastructure is already containerized and ALB routing is already service-aware
- Evaluate AWS Graviton (ARM) task definitions for 20% cost reduction when stable
